## 问题背景

想做一个自己的 AI 聚合站：网页上能切换不同模型聊天，后端统一收口，以后方便继续加功能。第一版目标定得很具体——能运行、能切换模型、能对话的 MVP，不追求 Vue、PostgreSQL、支付这些后续能力。

## 先练手：一键脚本的三个教训

动手自建之前，先照教程部署了一个现成的网关项目练手。过程不顺利，但教训比结果有用：

1. **复制脚本不等于理解配置。** 教程里让"把自己的内容写进 app.py"，实际那个 `app.py` 只是安装启动脚本，真正的业务配置在管理后台或环境变量里。分不清"启动脚本"和"应用配置"浪费了大量时间。
2. **一键脚本存在版本漂移。** 脚本直接拉取项目的 `main` 分支，项目更新后教程可能突然失效。Console 里出现 `requires Python >=3.13`、依赖构建失败这类报错，不是自己"没填对内容"，而是上游变了。
3. **要看第一处报错，不要盲目重启。** 启动半天没日志、或者反复重启时，正确动作是读 Console 最后几十行日志里的第一处报错，而不是反复点重启碰运气。

## 受限环境的选型约束

目标容器只给了大约 308 MiB 内存和 716 MiB 磁盘。这个约束直接决定了选型：

- 后端 Python + FastAPI，单进程运行；
- 数据库 SQLite，不上 PostgreSQL；
- 模型请求用 `httpx`；
- 前端原生 HTML/CSS/JavaScript，不引入构建链。

另一个容易踩的坑是端口：容器平台通过 `SERVER_PORT`/`PORT` 环境变量分配端口，应用必须读环境变量并监听 `0.0.0.0`，写死 127.0.0.1 或固定端口都会直接不可访问。

## 域名与端口限制

部署到一个高位端口后自然想绑域名，这里有个此前不知道的限制：普通 DNS 记录只把域名解析到 IP，不携带端口；而 Cloudflare 橙色云代理也不支持任意端口。所以"加一条 A 记录就能用 HTTPS 访问 `IP:高位端口`"这条路不成立，需要在前置层解决端口和 TLS，这也是 MVP 之后要补的一块。

## 架构设计：适配器模式

核心思路是前端永远只请求自己的统一接口，后端再按模型转发：

```text
浏览器 → /api/chat、/api/models
              │
        FastAPI 聚合层
              │
        BaseProvider 适配器抽象
        ├── openai_compatible（第一版只做这个）
        ├── anthropic（后续）
        └── gemini（后续）
```

`BaseProvider` 只约定两个方法：`chat(model, messages, stream)` 和 `list_models()`。大量服务兼容 OpenAI 的 `/v1/chat/completions` 与 `/v1/models` 接口，所以第一版只实现 `openai_compatible` 适配器，配 `API_KEY` + `BASE_URL` 就能接入一家新供应商。以后增加模型只是增加一个适配器文件，不改前端和主流程。

## 安全边界

- API Key 只放环境变量，不进前端代码、不进截图、不进仓库。
- 模型来源优先选择官方或明确授权的 API；来路不明的逆向接口有账号受限风险，不作为依赖。

## 当前验证范围

目前完成的是架构设计、目录骨架和选型决策，还没有可运行的转发代码，`/api/chat` 的端到端调用、容器内的启动行为、重启后的数据持久化都没有验证。

## 后续计划

先实现 `openai_compatible` 适配器和最小聊天页面，在容器里跑通一次真实的端到端对话；然后再考虑流式输出、用量统计、管理页，以及用域名和前置代理解决端口与 HTTPS 问题。
